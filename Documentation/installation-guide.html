Setup, start to finish

Installation guide

Everything needed to get FreightFast running from a fresh copy of the source — requirements, setup steps, configuration, and the fixes for the handful of things that most commonly trip people up. For what the product actually does, see the Documentation.

Requirements

Document uploads, SMTP/WhatsApp/SMS delivery, and AI features all work without their optional credentials configured — the app runs with those subsystems simply switched off until you supply keys.

02 — Setup

Installation

Seven steps from a fresh copy of the source to a running app with demo data loaded.

Install dependencies

From the project root:

npm install

Create the database

Create an empty MySQL/MariaDB database for the app. Using the MySQL CLI:

mysql -u root -p -e "CREATE DATABASE freight_control CHARACTER SET utf8mb4;"

Configure environment variables

Copy the example file and fill in your own values:

cp .env.example .env

At minimum, set DATABASE_URL to point at the database from step 2, and generate a random NEXTAUTH_SECRET. See Environment variables for the full list.

# macOS / Linux
openssl rand -hex 32

# Windows PowerShell
[Convert]::ToHexString((1..32 | %{ Get-Random -Max 256 }))

Generate the Prisma client

npx prisma generate

Push the schema

Creates every table in the database from prisma/schema.prisma:

npx prisma db push

Seed initial data

Creates the platform owner, a demo company, its default roles, and a set of demo staff accounts:

npx prisma db seed

Credentials for every account it creates are listed under Default accounts.

Start the app

For local development, with hot reload:

npm run dev

Then open http://localhost:3000. If port 3000 is already in use, Next.js picks the next free port automatically and prints it in the terminal — watch the startup output for the actual URL.

Upgrading an existing install? Re-run npx prisma db push (or apply the migrations under prisma/migrations/ in order) after pulling new code, then restart the app server. New tables and columns are additive and nullable by default, so existing data keeps working unchanged.

05 — Optional

Background jobs

Two features rely on an external scheduler hitting a protected endpoint. Both stay inert — the app works fine without them — until you set their secret.

Notification dispatch

Sends approved, queued email/WhatsApp/SMS notifications. In-app notifications work regardless; this only governs external delivery.

*/5 * * * * curl -fsS -X POST \
  -H "x-dispatch-secret: $NOTIFICATION_DISPATCH_SECRET" \
  https://your-domain.example/api/cron/notification-dispatch

Failed sends back off at 5min → 20min → 1hr → 4hr, up to five attempts, before landing in the Delivery Outbox for manual retry.

Recurring tasks

Generates due occurrences from recurring task templates. An hourly interval covers daily/weekly/monthly rules comfortably.

0 * * * * curl -fsS -X POST \
  -H "x-dispatch-secret: $RECURRING_TASK_DISPATCH_SECRET" \
  https://your-domain.example/api/cron/recurring-tasks

Without the cron configured, individual recurrences can still be caught up on demand from their detail page using Run now.

06 — Going live

Production deployment

A production build is a standard Next.js build — point it at a real database and a persistent process manager.

npm run build
npm run start

Before switching real users onto it: generate a fresh NEXTAUTH_SECRET (don't reuse the one from local development), point DATABASE_URL at your production database, run the same prisma generate → db push sequence against it, and set NEXTAUTH_URL to the real public URL.

The repository includes ready-made GitHub Actions workflows for deploying to an Azure Web App or a self-hosted VPS over SSH — both read their credentials from GitHub repository secrets rather than anything in this codebase, so they need no changes here to use; configure the corresponding secrets in your GitHub repository settings.

07 — If something's off

Troubleshooting

Sign-in fails with "JWT_SESSION_ERROR — decryption operation failed"+

This means a session cookie in your browser was encrypted with a different NEXTAUTH_SECRET than the one currently configured — typically because the secret was regenerated after a previous sign-in.

Clear cookies for the app's domain (or open it in a private window) and sign in again.

MySQL says "Access denied for user"+

The credentials or host in DATABASE_URL don't match a MySQL user that exists and has access to the target database. Verify the string against what you'd pass to the mysql CLI, including the host — 127.0.0.1 and localhost can resolve to different auth rules depending on your MySQL configuration.

The dev server starts on a different port than 3000+

Expected behavior — Next.js checks if 3000 is free and picks the next open port if not. The terminal output from npm run dev always prints the actual URL in use.

Prisma throws a validation error mentioning a missing relation+

Usually means the Prisma Client is out of sync with schema.prisma. Re-run npx prisma generate after any dependency install or schema change, then restart the dev server.

Seeding fails on a brand-new database+

The schema has to exist before it can be seeded. Confirm npx prisma db push completed successfully first — it should report the tables it created — before running npx prisma db seed.

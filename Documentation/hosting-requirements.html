Hosting requirements

FreightFast is a Node.js application, not a PHP script. It needs a host that can keep a Node process running continuously — most standard shared hosting plans cannot do this. Check this page before purchasing hosting.

01 — 30-second check

Is your hosting compatible?

Ask your host, or check your control panel, for these three things.

You needTypical shared cPanel hostingVPS / cloud server
SSH / terminal accessusually noyes
Ability to run a persistent Node.js processusually noyes
Your own MySQL/MariaDB database with remote or local accessoften yesyes

If your plan is marketed as "shared hosting for WordPress/PHP sites" and doesn't mention SSH access, it will not run this application. This is the single most common cause of a failed install — check this first, before buying.

03 — Confirmed to work

Where it runs

Anywhere you get a real Linux server with SSH access and can run npm run build && npm run start as a long-lived process.

Any VPS provider

DigitalOcean, Linode, Vultr, Hetzner, Contabo — a basic droplet/instance is enough to start.

AWS EC2 / Lightsail

Full control over the instance; pair with RDS for a managed database if desired.

Azure App Service

A ready-made GitHub Actions workflow for this is already included in the repository.

Self-managed VPS over SSH

A ready-made GitHub Actions workflow for SSH-based deploys is already included in the repository.

Docker host

Any server or platform that runs a Dockerfile you build from this codebase (Next.js standalone output works well in a container).

Serverless platforms (Vercel, Netlify, and similar): possible, but not the primary supported path. They require extra configuration for the database connection pooling Prisma needs under serverless invocation, and for scheduling the two background-job endpoints (which need a real cron trigger, not just an HTTP route). The two deploy workflows bundled with this codebase target a VPS and Azure App Service specifically because both give a persistent process and a normal system cron.

04 — Keeping it running

Process management & scheduled jobs

A process manager, not just npm run start

Running npm run start directly in a terminal stops the moment that terminal closes. In production, run it under a process manager that restarts it automatically — pm2, a systemd service, or a Docker container with a restart policy all work.

A reverse proxy in front of it

Next.js serves plain HTTP on its own. Put Nginx (or equivalent) in front of it for TLS/SSL termination and to serve on ports 80/443.

Cron access for two optional features

Automated external notification delivery and recurring-task generation both rely on something calling a protected URL on a schedule — a normal Linux crontab entry, or any external scheduler that can make an HTTPS request. Both features work perfectly well without this configured; they just don't run on autopilot until it is. See the Installation Guide's Background Jobs section for the exact commands.

What won't work

Hosting typeWhy not

PHP-only hostingThere's no PHP in this codebase to run; the host needs a Node.js runtime.
